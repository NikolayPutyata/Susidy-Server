# Susidy Server

Backend для суші-бару з доставкою: публічний каталог товарів, кошик і оформлення замовлення без обов'язкової реєстрації, а також адмін API для керування товарами та клієнтами.

## Стек

Node.js (ESM) + Express + MongoDB (Mongoose). Аутентифікація — сесії (access/refresh токени в БД). Логін і реєстрація — за номером телефону й паролем, без email. Зображення товарів зберігаються в Cloudinary. Сповіщення про нові замовлення надсилаються в Telegram.

## Запуск локально

```bash
cp .env.example .env   # заповнити значення
npm install
npm run dev
```

### Через Docker

```bash
cp .env.example .env   # заповнити Cloudinary/Telegram, MONGODB_URI можна лишити порожнім
docker compose up --build
```
Mongo піднімається окремим контейнером, API автоматично підключається до нього (`MONGODB_URI` для контейнера прописаний у `docker-compose.yml`).

### Створення першого адміна

Реєстрація через `/auth/register` завжди створює звичайного користувача (`role: "user"`). Щоб отримати адміна, заповніть `ADMIN_*` змінні в `.env` і виконайте:

```bash
npm run seed:admin
```

Скрипт створює користувача з `role: "admin"` (або підвищує роль, якщо користувач з таким телефоном вже існує).

## Основні сценарії

### Кошик: гість — тільки в браузері, акаунт — у БД

Гість (без логіну) взагалі не має кошика на сервері — весь кошик живе на клієнті (localStorage), бекенд про нього нічого не знає до моменту чекауту. Колекція `carts` зберігає поточний кошик **лише** залогінених користувачів (по одному кошику на `user_id`), і саме тому весь `/cart/*` API, крім чекауту, вимагає `Authorization: Bearer <accessToken>`.

При оформленні (`POST /cart/checkout`) обов'язкові `name`, `phoneNumber` і, для гостя, `items` (масив товарів з кошика на клієнті — сервер нічого не шукає в БД). Для залогіненого користувача `items` в тілі запиту ігноруються — сервер бере його кошик з `carts` і видаляє його після оформлення. Сервер шукає (чи створює) користувача за номером телефону:
- якщо такий телефон уже є в базі — замовлення прив'язується до існуючого користувача (новий запис не створюється);
- якщо немає — створюється мінімальний запис користувача (ім'я + телефон, без пароля).

Персональна знижка (`discount`, %) користувача застосовується автоматично до суми замовлення при оформленні.

Коли гість логіниться, його локальний кошик (на клієнті) просто відкидається, і фронт довантажує кошик з БД через `GET /cart/me` — жодного злиття немає, це свідоме рішення.

### Реєстрація/логін — за телефоном, опційні, сесія на 60 днів

Ідентифікація повністю по номеру телефону, без email. `/auth/register` приймає `name`, `phoneNumber`, `password`, необов'язково `city`. `/auth/login` — `phoneNumber` + `password`. Обидва лишаються опційними для клієнта (акаунт потрібен лише для історії замовлень, "Моїх замовлень" і персональної знижки, а не для самого замовлення). Якщо людина спершу замовляла як гість, а потім зареєструвалась тим самим номером телефону — її "гостьовий" запис користувача доповнюється паролем, а не дублюється.

`refreshToken`/`sessionId` кукі й `refreshTokenValidUntil` сесії живуть 60 днів (`SESSION_DURATION`) — після логіну користувач лишається залогіненим без повторного входу, поки не мине цей строк (короткоживучий `accessToken`, 15 хв, оновлюється мовчки через `/auth/refresh`).

Відновлення пароля через email наразі прибране; відновлення за номером телефону через SMS — заплановане на потім.

### Адмінка (`/admin`, потребує `role: "admin"`)

- `POST /admin/products` — створити товар (`multipart/form-data`, поле `images` — файли, до 10 шт., завантажуються в Cloudinary)
- `PATCH /admin/products/:id` — оновити товар (нові `images`, якщо передані, повністю замінюють старі)
- `DELETE /admin/products/:id` — видалити товар
- `GET /admin/users?page=&perPage=` — список усіх користувачів (з `ordersCount` — кількістю їхніх замовлень за весь час)
- `GET /admin/users/search?phone=` — пошук користувачів за (частиною) номера телефону (теж з `ordersCount`)
- `PATCH /admin/users/:id/discount` — встановити персональну знижку (`{ "discount": 10 }`, 0-100%)
- `GET /admin/users/export?from=&to=` — CSV-файл (Ім'я, Номер, Місто) людей, які зробили хоча б одне замовлення в діапазоні `[from, to]` (ISO-дати); без параметрів — за весь час
- `GET /admin/orders/today` — усі замовлення за поточну добу (межі доби рахуються за системним часом процесу — у Docker виставлено `TZ=Europe/Kyiv`; для локального запуску без Docker, якщо треба саме київська доба, запускайте `TZ=Europe/Kyiv npm run dev`)
- `GET /admin/orders/search?phone=` — усі замовлення конкретного клієнта за (частиною) номера телефону

## Змінні середовища

Див. `.env.example`. `MONGODB_URI` — повний connection string (Atlas: `mongodb+srv://...`, локально/Docker: `mongodb://...`). `CLOUDINARY_*` обов'язкові для роботи адмінського завантаження зображень. `CLIENT_ORIGIN` — origin(и) фронтенду, яким дозволено робити запити з кукі (сесія/refresh-токен зберігаються в httpOnly-куках, тому без правильного `CLIENT_ORIGIN` + `credentials: 'include'` на фронті логін/refresh не працюватимуть з іншого домену).

**Деплой на різні домени (наприклад, фронт на Vercel, API на Render/Railway):** обов'язково постав `COOKIE_SECURE=true`. Браузер вважає `susidy-client.vercel.app` і `susidy-api.onrender.com` різними сайтами, і без `SameSite=None; Secure` на кукі сесії він їх просто не надсилатиме — логін формально "спрацює" (API поверне `accessToken`), але після перезавантаження сторінки сесія одразу загубиться, бо `/auth/refresh` не побачить кукі. Локально (все на `localhost`) цей прапорець не потрібен.

## Публічне API

- `GET /products/all`
- `GET /products/category/:category`
- `GET /products/:productId`
- `POST /cart/checkout` — гість чи акаунт (див. вище)
- `GET /cart/me`, `POST /cart/add`, `PATCH /cart/items/:productId`, `DELETE /cart/items/:productId` — лише залогінені (`Authorization: Bearer`)
- `POST /auth/register`, `POST /auth/login`, `POST /auth/logout`, `POST /auth/refresh`, `GET /auth/me`
- `GET /orders/me` — історія замовлень поточного користувача (лише залогінені)

## Що поки не реалізовано

Статуси замовлень (наразі замовлення лише летить у Telegram і кошик очищається), rate limiting на `/auth`, пагінація товарів, відновлення пароля через SMS — свідомо лишили на потім за домовленістю.
